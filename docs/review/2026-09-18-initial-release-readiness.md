# techō 初版体验与发行准备评估

## 文档定位与证据边界

本文将项目讨论整理为供维护者和本地开发 agent 阅读的评估快照，目标是完善初版的完整使用路径，而不是扩大功能范围。阅读入口与历史文档分类见 [文档导航](../README.md)。

审阅基线为 [main 的 a7bc8b0](https://github.com/Noctsyndrome/techo/commit/a7bc8b0245e593ffc877c167c9031a80502a38fd)，其 `Cargo.toml` 声明版本 `0.1.0-alpha.2`。本次整理重新核对了仓库树、开发说明、原始设计与关键实施记录；源码判断沿用同一提交的静态审阅。基线的 [GitHub Actions run 34929299579](https://github.com/Noctsyndrome/techo/actions/runs/34929299579) 返回成功，但这不代表本文作者已经在三种操作系统上完成交互实测。[Cargo.toml][source-cargo] 与 [CI][source-ci] 是版本和检查配置的依据。

本文没有运行本地构建、单元测试、PTY 脚本或真实终端验收，没有验证 crates.io 上 alpha.2 源码包与当前 main 的逐文件一致性。用户已说明该版本发布于 crates.io；不要仅凭版本字符串相同，就认定两者发布内容一致。基线审阅时 GitHub Releases 列表为空，也没有二进制发行工作流。

文中的“静态确认”表示可以从指定代码路径推导出行为，不是已在真实终端复现。“建议验收”表示未来工作的完成条件，不是本次已完成的测试。本次评估没有实施下述产品改进、修改工作流、创建 tag 或发布版本；后续文档整理仅调整目录与链接，并将下文目录约定同步为用户确认的平铺结构。

本文是 `advisory` review，不是已批准的 spec。建议优先级不等于任务授权。尤其是改变 Esc 取消、新建时间、首启体验与手账日边界的提议，应先形成明确决定，再进入实现。

## 产品判断与应保留的边界

techō 的核心价值是：打开今天这一页，不必先设计组织方式，就能写下东西；过一阵子再回来，它仍处在容易理解的位置。日期、页面分区和时间提供适度秩序，不需要靠项目、标签体系或数据库视图来完成组织。

当前 Schedule、Todo、Free memo、月历和每日一言已经能够承载这一定位。每月印刷色、余白、已写日期的墨迹、就地编辑和一行上下文提示相互配合，形成的是一个安静的记录工具，而不仅是更换配色的任务列表。这一判断依据 [设计评审][source-design] 与 [后续实施记录][source-design-impl]，不是要求重新照搬原始评审中的每个具体方案。

继续保留页面本体的克制，不重新加入满屏快捷键、计数、常驻教程或繁重欢迎向导。借鉴现代 TUI 的重点是可发现性、混合输入和错误恢复，而不是复制其他应用的功能密度。界面安静不应以让用户猜测操作、记忆隐藏规则或担心内容丢失为代价。

初版暂不追求同步、重复日程、提醒、标签系统、双向链接、插件、复杂主题配置或应用内自动更新。长文本的基本编辑与可靠恢复属于记录工具的基础质量，不应因为“保持小巧”而被一概归为功能膨胀。

## R01：时间输入的 UTF-8 切片崩溃

证据位于 [journal.rs][source-journal] 的 `parse_time_input()`。函数先按 `String::len()` 的字节长度分支，再对三字节输入使用 `value[..1]`、四字节输入使用 `value[..2]`，但切片前没有排除非 ASCII 字符。

单个全角数字 `９` 或汉字 `中` 占三个 UTF-8 字节，会进入三字节分支并在字符内部切片。这条路径会触发 panic，而不是正常返回无效时间。编辑正文之后，将时间字段替换为该输入再保存，是需要补充的交互复现路径；本次没有运行此复现。

最小修复是在按字节切片之前验证允许的字符，非法输入返回错误。全角数字和全角冒号是否先规范化是额外的可用性选择，不是修复崩溃的前提，也不需要扩展为自然语言时间解析。

建议验收：普通数字、冒号、空串、空白、汉字、全角数字、emoji 与混合文本均不 panic；现有 `9`、`930`、`9:30`、`09:30` 行为保持兼容。非法输入后正文仍可继续编辑和保存。全角输入最终是被接受还是被拒绝，以选定的规范化策略为准。

## R02：取消与草稿恢复必须先做产品决定

[app.rs][source-app] 的编辑态 Esc 调用 `Action::Cancel`，直接清除 `editing`，不检查修改状态。磁盘上原有日记不因此消失，但本次未保存的改动会被放弃。

这不是一个可以直接认定为“漏写确认框”的 bug。[键位实施记录][source-keys-impl] 明确将“Esc 直接放弃草稿，不加确认”作为既有便签式交互决定。上一轮口头评估提出的保护性取消应视为重新评估该决定的建议，不构成覆盖它的授权。

建议维护者在真实记录场景中比较两种方案：继续保留立即取消，并清楚告知其含义；或者未修改时直接退出、有修改时显示保存、放弃、继续写，默认继续写。不要把 Esc 偷偷改成保存，也不要在一次小修复中擅自改变全局按键语义。

异常退出的恢复与用户主动取消是另一件事。可以评估单份本地恢复草稿，使 SSH 断线、窗口关闭或进程异常后有安全出口，而不必引入完整自动保存体系。是否保留被明确放弃的内容、保留多久、何时清理，需要明确且可理解；用户选择放弃后，不应又在下次启动时无解释地恢复。

建议验收：分别覆盖新建、编辑既有内容、未修改退出、保存失败、明确放弃、异常终止和重启。正式日记与恢复草稿的语义不能混淆，不能因保护草稿而覆盖外部修改或生成意外正式记录。实施前必须记录所选方案与既有决定的关系。

## R03：错误不能移除恢复入口

[ui.rs][source-ui] 的 `draw_editing_footer()` 在 `edit.error` 非空时只显示错误并立即返回，原本可点击的保存、取消和切换字段入口不再绘制。[app.rs][source-app] 的后续文字输入也不会自动清除该错误。键盘保存仍然可以工作，但依赖点击的用户失去了原先的操作入口。

建议将成功消息与错误状态分开：`Saved` 可以短暂替换提示，错误应保留至被修正或明确处理，同时不移除重试与离开入口。正常时维持一行页脚；错误时暂时多用一行，比坚持一行而隐藏操作更合理。内容过长时还需要能读到完整错误，而不是只保留截断片段。

打开日期失败、切换任务完成状态失败等非编辑错误，当前也会走通用的短时状态消息。这些错误不应按成功提示的节奏消失。

建议验收：非法时间、无效日期、写入失败、外部文件冲突后，分别用键盘与可用的鼠标入口完成修正、重试和退出；草稿持续存在；成功提示可淡出，尚未处理的错误不能静默消失。不要为了给鼠标加入口而改变键盘用户现有的保存方式。

## R04：优先修好基本写作手感

[editor.rs][source-editor] 中，`visual()` 按终端宽度显示自动折行，但 `vertical()` 只依据文本中的真实换行符 `\n` 移动。一段没有手动回车、却占据多个视觉行的文字，在显示上可以上下移动，当前光标逻辑却仍把它当作一行。这是从代码确认的行为，是否及如何调整需要以编辑体验为目标。

建议优先实现自动折行后的上下移动，并在中英文混排中保持合理的视觉列位置。随后评估有限的撤销与重做，而不是把编辑器扩展为完整 IDE。鼠标点击正文目前不等于把光标放到所点字符，暂不应宣称具备完整的桌面式文本操作。

当前左右移动和删除主要按 Unicode 标量值处理，显示宽度也按字符累积。普通汉字测试不能代表组合字符、带肤色修饰的 emoji 或 ZWJ 序列都能自然编辑；这些需要专门验证。实现可选择合适的字素簇与显示宽度处理方式，但本文没有指定依赖或授权重写编辑器。

建议验收：长段落自动折行后上下移动；中英文宽度混排；短行与长行之间移动；组合字符和 emoji 的左右移动、退格、删除；多行粘贴后的修改；窗口缩放后光标仍可见。若加入撤销，需覆盖输入、粘贴、删除和重做，并明确一次撤销的粒度。

## R05：首次写入与完整帮助分离

[app.rs][source-app] 的 `App::open()` 使用 `help: written.is_empty()`，默认焦点为 Schedule。用户启动后不写入就退出，下一次仍会看到帮助；这不是独立的“已完成首启引导”状态。[ui.rs][source-ui] 的帮助是 page、dates、year、note、journal 五组完整参考，较小终端需要滚动。

完整键位表适合随时查询，不一定适合作为第一次见面。建议让今天的页面先可见，用可跳过的短提示帮助完成一次真实写入：Enter 开始，时间已有默认值，Ctrl+S 保存。第一次成功后再提示帮助入口与本地保存位置。不要强制填写目录、选择主题或学习所有面板，也不要往日记里插入示例内容。

首次引导状态应独立于是否存在日记文件；跳过引导不应靠写一个空日记来标记。已有 `?` 键位参考继续保留，不能因为新引导而破坏已经建立的查阅入口。

默认落在 Schedule 并非确定错误：自动带时间的记录可以成为自然的入口。是否改为 Free memo 需要体验决定，不能仅引用更早实施记录中“默认 memo”的描述就回退当前行为。

建议验收：全新目录第一次启动可快速完成一条记录；不写入并跳过后，下一次不会反复被同一引导阻塞；帮助始终可以主动打开；引导状态与日记内容互不污染。建议邀请未读说明的人走完这一流程，而不只检查帮助文本是否渲染。

## R06：新建时间与末尾 Down 的隐藏规则

[app.rs][source-app] 的 `new_item_time()` 会优先继承当前条目的时间；当天列表末尾 Down 触发 `append()` 时则改用当前时间。因此两种新建路径可能得到不同默认值。[设计实施记录][source-design-impl] 说明这服务于同一时刻归并和快速追加，属于有意设计。

建议评估用户在“记录刚发生的事”和“给同一时间补一条”之间的真实频率。候选调整是把当前时间作为更容易发现的新建路径，同时保留同一时刻补充的能力；也可以维持当前规则，但让上下文提示足够清楚。不要未经决定统一成另一种规则。

还应实测按住 Down 或 j 浏览到列表末尾时的体验：导航转入编辑是否出乎预期，重复事件是否让用户意外进入输入状态。这里提出的是待验证场景，不宣称本次已经复现故障。

建议验收：空列表、选中旧条目、列表末尾、历史日期、相同时间多条记录及连续按键，各自的新建落点与文案符合选定规则。鼠标滚轮继续只浏览，不应意外创建记录。

## R07：统一说明 04:00 与“今天”的语义

[journal.rs][source-journal] 的 `ScheduleEntry` 以 04:00 为排序起点，凌晨条目在输出中标记 `(+1)`；[main.rs][source-main] 启动日期以及 [app.rs][source-app] 返回今天的逻辑使用当前公历日期。

必须先决定 04:00 只是纸页内的排序方式，还是整个应用的手账日边界。例如公历 9 月 18 日凌晨一点，记录“刚发生的事情”应属于 9 月 17 日的延伸，还是 9 月 18 日？不能一边按公历默认打开，一边在用户没有意识到的情况下赋予次日的含义。

如果选择手账日语义，建议集中封装日期和当前时间的计算；如果只是排序语义，应清楚解释凌晨标签与实际日期的关系。不要在此次调整中自动搬迁既有文件或猜测旧记录的真实发生时间。

建议验收：午夜、03:59、04:00、跨月、跨年和闰日；启动、返回今天、新建默认时间、`(+1)` 展示及保存文件名保持一致。编辑中跨越边界时不自动切页，不丢失草稿。时间相关测试应使用可控时钟或显式时间输入，避免随现实日期变化而失效。

## R08：已有存储保护之上，补齐安全出口

[storage.rs][source-storage] 已有目录锁、同目录临时写入、`sync_all()` 后重命名、保存前外部修改检查、旧格式备份，以及只浏览不创建日记的行为。这些值得保留。它们降低了保存风险，但不代表未提交草稿已持久化，也不是对所有文件系统、并发编辑和断电情形的绝对保证。

外部修改冲突目前会保留编辑状态，但提示用户自行复制草稿再重新打开日记。建议提供一个小而明确的恢复出口：将草稿另存为独立恢复文件并显示完整路径，再允许重新载入正式日记。不必做复杂合并界面，也不能静默覆盖磁盘内容。若原目录不可写，恢复失败仍需明确提示，不能虚报已保存。

数据位置已经出现在帮助中，但长路径可能被截断。可考虑新增 `techo --print-data-dir` 一类只打印完整路径的命令；这是建议命令，不是当前功能。安装说明应写清楚程序与日记分离、升级只替换程序、卸载默认保留数据，以及怎样备份和迁移目录。macOS 的当前目录也应明示，而不是因为它使用非 Windows 分支而留给用户猜测。

另一个边界来自 [journal.rs][source-journal]：文件是具有固定章节与元数据的 Markdown，不是任意 Markdown 都可以无损往返的通用编辑格式。`to_markdown()` 会重建固定前置元数据，解析器并没有保留任意自定义字段；不能承诺用户额外加入的 tags 或其他元数据都会原样留下。

建议明确可自由编辑的区域，对额外元数据选择保留或拒绝有损保存，并提供可理解的错误说明。初版不要求兼容所有 Markdown 变体，但不得把格式约束隐藏在“纯 Markdown”的宣传之后。

建议验收：两实例争用目录、外部编辑、保存失败、恢复文件写入失败、旧格式备份、额外元数据、备份后恢复，以及升级后继续读取日记。覆盖原有保护的测试应保留；所有失败路径都应能区分正式保存、仅有内存草稿和已经写出的恢复副本。

## R09：布局与真实终端验收

[ui.rs][source-ui] 的完整双栏页面要求至少 86 列且高度充足；80 列布局不绘制月历，而标题主要显示月日，年份原本由月历承担。浏览历史日期时，窄屏会失去年份上下文。更窄时只显示当前面板，需要让用户知道仍可切换到其他区域。

建议窄屏标题保留完整日期语境，在单面板状态下提供很轻的切换提示或入口。不要为解决窄屏问题把宽屏重新变成布满按钮的控制台。鼠标与键盘应共享焦点和选中状态，但不必宣称所有动作都能只用鼠标完成。

[CI][source-ci] 在 Linux、macOS、Windows 执行检查和构建，PTY 脚本实际仅在 Linux 运行。[Releasing][source-releasing] 仍称 Linux 与 macOS 都跑 PTY；[Development][source-development] 的命令注释也写了 Linux/macOS，而下方说明正确写为仅 Linux。这些需要统一为准确的支持与验证声明。

[键位实施记录][source-keys-impl] 已明确说明尚未在真实 macOS 终端验证。构建成功不能据此升级成“macOS 操作已验证”；PTY 时序问题也不能仅凭其他平台正常就认定应用完全无关。[main.rs][source-main] 的 `--keys` 与键盘增强协议探测是诊断工具，协议开启也不保证被终端或系统截获的每个组合键都能抵达应用。

建议用同一条流程验证 Windows Terminal/PowerShell、macOS Terminal.app 及一种支持增强协议的终端、Linux 本地 UTF-8 终端与 SSH；有实际需求时再覆盖 tmux。记录终端、操作系统、架构和结果，不只写平台名称。

建议验收流程：从干净安装开始，首启写入一段中英文混合文本，确认输入法候选不误触提交，粘贴多行并编辑自动折行段落，制造一次非法时间并恢复，保存退出后重新打开，跳到历史年份，缩小至 80×24 和单面板布局，再验证取消策略、鼠标选择及退出后的终端状态。最小尺寸以下应安全提示，不能丢草稿。验收应针对实际发行二进制，而不只是开发机 debug 版本。

## R10：预编译发行与低负担安装

### 建议的最小发行目标

优先把四类用户环境做好，能够验证更多架构时再增加。下面是建议矩阵，不是已经发布或测试通过的平台声明。

| 面向用户的名称 | Rust target | 建议压缩包 |
| --- | --- | --- |
| Windows 64 位 | `x86_64-pc-windows-msvc` | `.zip`，包含 `techo.exe` |
| Mac Apple Silicon | `aarch64-apple-darwin` | `.tar.gz` 或明确配置的 Unix 归档格式 |
| Mac Intel | `x86_64-apple-darwin` | `.tar.gz` 或明确配置的 Unix 归档格式 |
| Linux 64 位 | 优先验证 `x86_64-unknown-linux-musl` | `.tar.gz` 或明确配置的 Unix 归档格式 |

这些 target 出现在 [cargo-dist 配置参考](https://axodotdev.github.io/cargo-dist/book/reference/config.html#targets) 中，但本项目能否正确构建并运行仍须验证。Linux 可优先尝试静态 musl 来减少 glibc 依赖；选择 GNU 构建时明确最低 glibc 和构建基线。Windows 需检查 CRT 依赖，macOS 需明确最低系统版本；不能把“有一个二进制文件”等同于任何同架构机器都能运行。

GitHub 下载入口应先使用用户可识别的平台名称，再展示 target，不要求首次安装者理解 Rust 工具链术语。

### 优先评估 cargo-dist，而不是维护自制安装生态

建议采用 GitHub Releases 承载可执行文件，并优先评估 cargo-dist 生成发布工作流。其 [Rust quickstart](https://axodotdev.github.io/cargo-dist/book/quickstart/rust.html) 覆盖归档、安装器及 GitHub CI 生成。它属于维护端工具，不是终端用户的前置依赖。手写矩阵也可行，但需要自行持续维护归档、平台识别、安装路径与发布流程。

初始化阶段可以使用下列命令；本次未执行，生成配置后必须审阅，不能直接视为满足项目要求：

```sh
# 先按官方说明安装并选定 cargo-dist 版本。
dist init
dist plan
dist build
```

具体配置位置、runner 和选项应依据实施时锁定的 cargo-dist 版本生成，不复制过时配置片段。[配置参考](https://axodotdev.github.io/cargo-dist/book/reference/config.html) 明确区分 target、工具版本、归档和运行库等选项。`dist plan` 只检查计划，不代表已经构建或验证。

第一阶段提供直接下载，加可选的 [Shell 安装器](https://axodotdev.github.io/cargo-dist/book/installers/shell.html) 和 [PowerShell 安装器](https://axodotdev.github.io/cargo-dist/book/installers/powershell.html)。安装路径和 PATH 变更要可见，失败要有可执行的下一步；不要求管理员权限作为默认体验。

随后再评估自己的 [Homebrew tap](https://axodotdev.github.io/cargo-dist/book/installers/homebrew.html)，使用预编译归档并借助包管理器升级。alpha 与正式版需考虑渠道隔离，不能让测试版无意替换稳定渠道。初版不必同时建设多个包管理器仓库、原生安装包与应用内更新器。

每个版本应包含可执行文件、许可证、简短运行说明及 [SHA-256 校验文件](https://axodotdev.github.io/cargo-dist/book/artifacts/checksums.html)。校验和用于核对文件，不应被当作签名或来源可信性的替代品。

### 发布应有明确边界和版本对应

现有 [Releasing][source-releasing] 强调人工发布、不可复用版本和非默认创建 tag。引入二进制发行会改变其中一部分流程，应先更新发布决策与操作文档；本文没有授权执行发布或 tag 操作。

建议新流程保持“人工决定里程碑、自动完成构建与上传”：确定候选提交和版本，完成检查，生成并测试四个平台的归档与安装路径，所有承诺支持的目标通过后再对外公布。crate、tag、提交和二进制应能互相对应，失败不得留下被误认为完整发行的半套产物。

历史 alpha.2 不应因为当前 `Cargo.toml` 仍叫该版本，就直接用新的 main 内容补出同名二进制。先核对已发布源码对应的提交；能够证明内容一致时才考虑补齐，不能证明时选择新版本。已经发布的版本内容不应通过替换源码或挪动 tag 来重新定义。

根据 [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)，draft 与 prerelease 不作为 latest。alpha 安装说明应指向明确版本，不能假定 `/releases/latest` 会选中预发布。正式版再给出稳定安装入口。

验证和发行的触发方式是两件事：当前检查工作流是手动触发，不需要为了增加 release 就强制每次 main 推送都发布，也不应把生成器的默认行为未经审阅当成项目决定。保留现有测试，并对实际 release target 的产物做冒烟验证。

### 安装、升级和退出产品的路径

README 目前主要展示 `cargo install --path . --locked`，是源码检出的安装方式。预编译发行上线后，把无需 Rust 的路径放在普通用户入口；源码安装作为后备方式，可说明 `cargo install techo --version 0.1.0-alpha.2 --locked` 对应指定 crate 版本。本次没有在干净环境验证该命令，也不把它描述为已验证安装。

需在没有 Rust、编译器和开发机隐藏依赖的环境中验证下载、解压、运行、PATH 生效、版本查询和二次启动。Windows 说明从终端启动；macOS 与 Windows 记录实际签名、安全提示和处理流程，不把关闭系统保护作为默认安装步骤。签名与公证的具体方案按实施时官方要求单独验证。

升级只替换程序，不覆盖日记；卸载默认保留日记，并明确数据路径。恢复或迁移数据不需要账号、网络或绑定某个包管理器。发行包和验证日志不能包含私人日记、绝对个人路径或发布凭据。

建议验收：四种目标的已声明环境中完成无编译安装与完整记录流程；校验和对应实际归档；程序版本、tag 与源码基线一致；升级后旧数据仍可读；卸载后保留数据；预发布安装入口不误指稳定版或不存在的 latest。尚未验证的环境明确标注，不扩大平台承诺。

## 文档结构：采用平铺的 review 与 spec

按维护者确认的简化方案，持续维护的 `guide.md`、`keys.md`、`files.md`、`development.md`、`releasing.md` 保留在 `docs/` 根目录；评审归入 `review/`，方案与实施记录归入 `spec/`，不再设置主题子目录。入口是 [文档导航](../README.md)。

review 和 spec 使用 `YYYY-MM-DD-topic.md`。实施记录与对应文档平级，沿用相同日期和主题前缀，命名为 `YYYY-MM-DD-topic-impl-notes.md`。已有评审对应的实施记录也保留在评审旁边；原本没有独立 spec 的记录不补造需求。文件名前缀不随修订变化，实际实施与验证日期写入正文。

spec 标明状态，实施记录说明实际取舍与验证，review 保留基线与建议属性。已完成方案不是自动待办，目录归类也不改变原有设计决定。时间标尺、保存与 Esc 等主题仍需结合对应实施记录理解，不能仅凭文档新旧决定覆盖什么。

本次目录整理已迁移历史文件并更新导航及相对链接；产品改进仍未实施，也不增加全仓库 agent 规则或额外强制流程。文末固定提交的源码与历史文档链接保留为审阅证据，不因当前文件迁移而改指其他基线。

## 下一轮实施的切片建议

建议先选 R01 与 R03 这类边界明确的问题，保留其余界面与键位。在独立的小变更中补测试、实施记录和必要说明，避免与发行框架或视觉调整混成一批。

随后用真实记录场景决定 R02、R05、R06、R07 的取舍，再完善 R04、R08、R09。若维护者暂不改变某个既有交互，应记录决定与剩余风险，而不是让 agent 反复尝试“修复”同一个有意行为。

发行准备可以并行规划，但应建立在通过完整记录流程的候选版本上。下一次 alpha 可作为无编译安装的试点；正式初版以支持环境中的完整流程与恢复能力为准，而不是以功能数量为准。

跨日搜索可以在基础质量稳定后再评估；它比更多装饰更接近长期使用需求，但无需为初版建立复杂索引系统。主题扩展、同步、插件与复杂日程继续后置。

本地 agent 开始时应读取当前任务、本页的建议顺序及相关源码；逐项确认是否仍适用于当前提交。选中的产品改动先形成获确认的 spec，实施后另写记录并更新当前说明。不要把本页改成没有基线、不断追加且真假完成状态混杂的总任务堆。

## 初版完成的判断

一个未读过文档的人，能够安装并打开今天，写下几句话，写错后自然改正，遇到错误知道如何恢复，离开时理解哪些已保存，下一次回来仍能继续写；升级或换工具时，数据也仍属于自己。

这个标准不要求 techō 大而全。它要求页面保持克制，而动作、状态和数据都值得信任。
